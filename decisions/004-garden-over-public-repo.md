# ADR-004: Digital Garden 而不是公開工作 Repo

## 狀態
已採用（2026-03-08）

## 背景
備份系統改造完成後，想公開這個案例讓別人看到思考過程。評估了怎麼公開。

## 考慮的選項

### A-1) 工作 repo 直接公開（保留 commit history）
- 需要 filter-repo 清洗歷史中的 email
- memory/、USER.md 等私有檔案要從 git 移到 vault
- 腳本中的 email 要改成環境變數
- **問題：** 移走的 memory/ 恰好是最有展示價值的（思考過程）
- **問題：** 以後每次 commit 都要注意不洩漏敏感資訊
- **問題：** 腳本改用環境變數後，工作環境多了一層間接

### A-2) 砍掉歷史，只留最新版
- 簡單，但失去 commit history（大神會看的）
- 一個 commit 的 repo 沒有故事性

### A-3) 砍歷史 + 重建敘事性 commit
- 分步 commit 重建「架構 → 備份 → 自動化」的故事
- 比 A-2 好，但看得出是人造的（所有 commit 同一天）
- commit history 的價值在於真實性

### B) Fork 乾淨版 + Digital Garden
- 工作 repo 保持私有，零改動
- 另建公開 repo，策展後的內容
- 私有檔案不用搬家，備份系統不用動
- 可以從 memory/ 摘取最有價值的片段，脫敏後放進 stories/
- 持續生長，不是一次快照

### C) 只寫文章
- 最輕量
- 但缺少「自己去翻程式碼」的說服力

## 決策
選 B — Digital Garden 模式。

## 決策過程

這個決策經過了多輪「檢查與驗證」：

1. **一開始選了 A-1** — 覺得「原始 repo 最真實」
2. **做風險掃描** — 發現 email、客戶名、路徑散布各處
3. **評估脫敏工作量** — 2-3 小時，且有邊界情況（KJ 只有 2 個字元）
4. **發現核心矛盾** — A-1 要求把最有價值的 memory/ 藏起來
5. **查了大神做法** — Mathias Bynens 用 `.extra` 分離，但他公開的是 dotfiles 不是工作系統
6. **查了趨勢** — Digital Garden（Maggie Appleton）最符合「展示思考演化」
7. **驗證備份影響** — B 方案對現有備份系統的影響是零
8. **最終確認** — 簡單管理 > 複雜脫敏

## 原因
- **工作環境不該為了展示而改變** — 這是根本原則
- **最有價值的內容需要策展** — memory/ 原始內容太私密，摘取精華更好
- **維護負擔要趨近零** — 不用擔心每次 commit 洩漏
- **Digital Garden 允許持續生長** — 不是一次性公開，是持續的過程

## 後果
- 需要維護兩個 repo（但 garden 是隨興更新，不是每天）
- 需要手動從工作 repo 摘取內容到 garden（未來可部分自動化）
- 讀者看不到原始 commit history（但看到的是整理過、更有價值的敘事）
- 這本身就是一篇 story（meta！）
